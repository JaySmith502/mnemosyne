**bootstrap.ts:**

Import `buildKnowledgeIndex` from `../knowledge/knowledge_index.js`. Import `EntityIndex` from `./entity-index.js`. Import `resolveOrCreate` from `./matcher.js`. Import types from `./types.js`.

Export `async function bootstrapEntityIndex(entityIndex: EntityIndex, options?: { skipLLM?: boolean; batchSize?: number }): Promise<{ indexed: number; merged: number; skipped: number; newEntities: number }>`

This function reads the current knowledge index and ensures every person/organization has a corresponding entity index entry. It runs incrementally — if an entity already exists in the entity index (matched by email or name), it updates rather than duplicates.

Logic:

1. Build the knowledge index: `const knowledgeIndex = buildKnowledgeIndex()`
2. Initialize counters: `{ indexed: 0, merged: 0, skipped: 0, newEntities: 0 }`
3. Process people in batches (default batchSize = 100):
   - For each person in knowledgeIndex.people:
     a. Skip if person has no name (can't create meaningful entity)
     b. Build candidate: `{ name: person.name, email: person.email, organization: person.organization, role: person.role }`
     c. Call `resolveOrCreate(candidate, entityIndex, { skipLLM: options?.skipLLM ?? true })`. Note: skipLLM defaults to true for bootstrap — we use deterministic + fuzzy only during migration to avoid expensive LLM calls on potentially thousands of entries.
     d. If `isNew`: increment newEntities. The new entity gets:
        - sorRefs: `[{ system: 'knowledge', id: person.file }]` — anchored to the knowledge note file
        - sources: `[person.file]`
        - aliases: map person.aliases to `{ type: 'name_variant', value: alias, confirmedBy: 'system', confirmedAt: now, confidence: 0.9 }`
     e. If not isNew (merged): increment merged. Update the existing entity:
        - Add person.file to sources if not already present
        - Add `{ system: 'knowledge', id: person.file }` to sorRefs if not already present
        - Add any new aliases from person.aliases
     f. Increment indexed
   - After each batch: call `entityIndex.save()` to persist progress (prevents data loss on interruption)

4. Process organizations similarly:
   - For each org in knowledgeIndex.organizations:
     a. Skip if no name
     b. Build candidate: `{ name: org.name, email: org.domain ? undefined : undefined, organization: org.name }`
     c. If org has a domain, try matching by domain in existing entities (check if any entity's email domain matches org.domain). This is a heuristic — not perfect but catches common cases.
     d. Call `resolveOrCreate` with skipLLM=true
     e. Track same counters as people
   - Save after each batch

5. Final save + return stats

**Performance considerations:**
- skipLLM=true by default during bootstrap (deterministic + fuzzy only)
- Batch saves every 100 entities (not every entity — reduces disk I/O)
- The resolveOrCreate call uses EntityIndex's in-memory maps for O(1) lookups, so the O(n*m) worst case only applies to fuzzy matching, which is bounded by FUZZY_MAX_CANDIDATES=5

2. In `processAllSources()`, AFTER all source processing is complete (after the `if (!anyFilesProcessed)` block at the end), add entity index bootstrap:

```typescript
// Bootstrap entity index from knowledge entries
// Runs incrementally — only indexes entries not yet in entity index
try {
    const entityIndex = new EntityIndex();
    entityIndex.load();
    const stats = await bootstrapEntityIndex(entityIndex, { skipLLM: true });
    if (stats.newEntities > 0 || stats.merged > 0) {
        console.log(`[GraphBuilder] Entity index updated: ${stats.newEntities} new, ${stats.merged} merged, ${stats.skipped} skipped`);
    }
} catch (error) {
    console.error('[GraphBuilder] Error bootstrapping entity index:', error);
    // Non-fatal — don't break the graph builder if entity resolution fails
}
```

Key design decisions:
- Run AFTER graph build, not during — the knowledge index needs to be up-to-date first
- Run on EVERY cycle (not just when files were processed) — catches manually edited knowledge notes too
- `skipLLM: true` — bootstrap is deterministic+fuzzy only (LLM matching is for runtime entity resolution from new data sources, not bootstrap)
- Wrapped in try/catch — entity resolution failure must NOT break the existing graph builder
- Only log when something actually changed (avoid noise in logs)

Do NOT modify any other function in build_graph.ts. The existing `buildGraph`, `buildGraphWithFiles`, `createNotesFromBatch`, etc. remain unchanged.
