Help me explain oe understand the "system of record" concept as it relates to the difficulty of widespread ai adoption in a business
A “system of record” is the authoritative place a business keeps a particular kind of data (customers, invoices, HR, etc.), and that role is exactly why broad AI adoption is hard: most current AI is great at “reading” from those systems, but scary when it starts “writing” back into them.

What “system of record” actually means
A system of record (SOR) is the authoritative source of a given slice of business data (customer, product, HR, finance, etc.).

Think CRM as the customer SOR, ERP as the financial SOR, HRIS as the employee SOR; everyone agrees “if it’s not in here, it didn’t happen.”

SORs enforce one canonical version of truth (data model, business rules, validation) so reports, compliance, and operations are consistent.

In conversation: “Salesforce is their system of record for customer data; QuickBooks is their system of record for financials.”

Why this makes AI adoption hard
1. AI wants flexibility; SORs are rigid
Legacy SORs (ERP, core banking, old line-of-business apps) were built for highly structured, transactional workloads, not for unstructured data and real-time model inference.

Architecturally, they tend to be monolithic, with rigid schemas and outdated APIs, which makes plugging in modern AI agents or vector layers painful.

Illustration you can use: “LLMs are like very smart interns that want to read everything and suggest changes; SORs are like locked filing cabinets with very specific forms and procedures.”

2. Data fragmentation vs “single source of truth”
In practice, organizations rarely have one clean SOR; they have overlapping SORs and a ton of “systems of convenience” (Excel, email, niche tools), leading to silos.

AI needs broad, high-quality, consistent data access; fractured SOR landscapes mean the model either sees only partial truth or has to reconcile conflicting truths.

So you end up with an AI copilot that says something plausible but doesn’t match “the numbers in SAP,” which kills trust.

3. Read-only AI feels safe; write-capable AI touches the crown jewels
As long as AI is a “system of engagement” layer that only reads from SORs (summarizing, searching, copilots in email/CRM), risk feels manageable.

The real leverage comes when AI becomes a “system of action/agents” that initiates workflows and writes back to SORs (creating orders, approving refunds, updating customer records).

The moment AI writes back, you hit questions of change control, audit trail, who’s accountable if the record is wrong, and whether those records stand up to regulatory scrutiny.

That’s why a lot of orgs stall at “AI assistant that drafts” instead of “AI agent that commits.”

4. Compliance, risk, and governance are anchored to the SOR
SORs are where regulated, auditable data lives: financial ledgers, health records, core customer data.

Controls, approvals, and audit procedures are built around human-driven changes to those systems, not autonomous or semi-autonomous AI updates.

For highly regulated sectors, the fear is not “bad answer in chat,” it’s “AI polluted the ledger/CRM and we based real-world decisions and filings on it.”

So the bar for letting AI near the SOR is way higher than letting it near email or internal docs.

A framing you can use with clients
You can explain the landscape as three layers:

Systems of record: Authoritative databases (ERP, CRM, HRIS, core banking).

Systems of engagement: Apps people actually use day-to-day (email, chat, portals, mobile apps) that sit on top of SORs.
​

Systems of action/agents: Emerging AI layers that decide and act by reading from SORs and then triggering workflows or writing back.

Then connect it to adoption friction:

“It’s easy to add AI to engagement” (search, summarization, chat over docs) because it’s mostly read-only.

“It’s hard to let AI touch the system of record” because that’s where truth, money, and regulators live.

Therefore, the bottleneck for widespread AI adoption isn’t just model quality; it’s redesigning how SORs expose APIs, enforce validation, log changes, and support AI-driven workflows safely.

What Rowboat gives you technically
Rowboat builds a local-first knowledge graph from raw work artifacts (emails, notes, files, etc.), turning them into linked entities like people, projects, orgs, and topics.

Each node is just Markdown with backlinks, so humans and agents can both read/edit it; background agents continuously parse new input and perform entity resolution to keep the graph coherent.

The graph then acts as a structured memory/index that agents query before they act, rather than re-embedding everything every time like a pure vector-RAG setup.

For a client, you can call this a “local AI memory layer” or “knowledge graph brain” that everything else plugs into.

Help me understand how I consolidate across multiple users in an org
Consolidating knowledge across multiple users in an org is the make-or-break for your sherpa idea—it's what turns it from "personal assistant" into "team memory."

Here's the simplest, most reliable way to do it without drowning in complexity.

Core principle: Shared graph, private events
One canonical graph per org: All users contribute to the same knowledge graph (clients, matters, decisions). No silos.

Events stay scoped: User A’s emails/notes only become graph-visible if they reference shared entities (clients, projects) and pass a sharing rule.

Provenance always tracked: Every node/edge shows "created by X, last updated by Y from email on date Z."

Step-by-step consolidation
1. Entity resolution (the hard part, but automatable)
Every user’s stream generates candidate entities. You consolidate them into "the one true node" using:

text
Three signals, ranked by strength:
1. Exact match on shared SOR ID (Clio matter #1234 → canonical Matter node)
2. Fuzzy name + org/email domain (Acme Corp @ Smith → link to existing Acme)
3. LLM confirmation ("does this email thread describe the same client?")
Start with SOR as the anchor: if Clio says "Acme Corp (ID 456)," everything mentioning Acme Corp links back to node 456.

For non-SOR entities (ad-hoc projects, internal decisions), use email domain + name + LLM to cluster.

Result: One Client_Acme node with edges from 5 users’ events.

2. Event normalization + sharing tiers
Normalize every event to a standard shape:

text
{
  type: "EmailSent" | "Meeting" | "DocCreated" | "SORUpdate",
  actors: ["user@org.com", "client@acme.com"],
  entities: ["Client_Acme", "Matter_2025Audit"],
  content: "extracted summary + raw link",
  private: true/false  // user sets or auto-inferred
}
Sharing logic (user-configurable, defaults safe):

Private: Only visible to sender + explicitly shared people

Team: Visible to users on same matters/clients

Org-wide: Client-facing work, SOR-synced data, decisions tagged #team

3. Graph update rules (keeps it sane)
When User B's event mentions entities worked on by User A:

text
IF event.entities intersect existing graph entities:
  → Link event to those canonical nodes
  → Add as timeline event on those nodes
  → Notify relevant users ("New activity on Acme")

IF event introduces new entities:
  → LLM proposes: "Is this the same Acme as Client_Acme-456?"
  → User A/B votes → Graph updated or new node created
